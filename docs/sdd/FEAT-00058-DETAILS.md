# Build Plan
1. **Spec doc** — Create `docs/frontend/global-search-mockup-spec.md` documenting the dropdown mockup (ASCII layout), grouping rules (Players / Clubs / Matches sections, each capped to top N, e.g. 5, results, "no results" state per group, overall empty/loading states), and the debounce/min-length behavior, following the style of `docs/frontend/match-search-filters-mockup-spec.md`.

2. **Backend: reuse existing free-text search for Players and Clubs** — No change needed to `FindFederatedPlayersByStringInNameQuery`/`FindClubsByStringInNameQuery`: both already support a null/omitted `source`, searching across all sources (confirmed in `FindFederatedPlayersByStringInNameQueryHandler` and `FindClubsByStringInNameQueryHandler`).

3. **Backend: new free-text match search (source/season-agnostic)** — `MatchSearchCriteria` (`tt-data-league-core-domain/.../match/model/MatchSearchCriteria.java`) hard-requires `source` and `season`, and `MatchRepository.searchMatches`/`countMatches` (JPA impl in `MatchRepositoryHelper`) always filters by both, so the existing match search cannot be reused as-is for a global query-only lookup.
   - Add `FindMatchesByStringInNameQuery` (+ `@Named` `FindMatchesByStringInNameQueryHandler`) in `tt-data-league-core-domain/.../match/find/`, mirroring the player/club query shape: `(String stringToSearch)`, splitting into whitespace fragments and OR-matching against player name and club/team name, ordered by `dateTime desc`, capped to a fixed limit (e.g. 5) — no `source`/`season` parameters.
   - Add a new default method to `MatchRepository` (e.g. `findAllMatchesByFragmentsInName(List<String> fragments, int limit)`) and implement it in `MatchRepositoryJpa`/`MatchRepositoryHelper` as a new JPQL `@Query` with `Pageable`/`limit`, omitting the `source =` / `season =` predicates that the current `search`/`countSearch` queries hard-code.
   - Reuse `MatchSearchReadModel` as the handler's response shape so the existing `MatchDto.from(...)` mapping in `tt-data-league-api-rest` can be reused unchanged.

4. **Backend: aggregating global-search endpoint** — Add `GlobalSearchController` (`tt-data-league-api-rest/.../search/GlobalSearchController.java`) exposing `GET /api/v1/search?q=<query>`, guarded by the same read permissions already required by the individual endpoints (`players:read`, no extra permission for clubs per current `ClubController`, `matches:read`), which:
   - Rejects `q` shorter than 2 chars the same way the player/club handlers already do (mirror the existing "too short" fail behavior instead of duplicating validation ad hoc).
   - Pushes `FindFederatedPlayersByStringInNameQuery(q)`, `FindClubsByStringInNameQuery(q)`, and the new `FindMatchesByStringInNameQuery(q)` through the existing `QueryBus`, mapping each result list through the existing `PlayerDto.fromObject`, `ClubDto.fromObject`, `MatchDto.from`.
   - Returns a single `GlobalSearchResponse(List<PlayerDto> players, List<ClubDto> clubs, List<MatchDto> matches)` record; a query-bus failure for one group degrades to an empty list for that group rather than failing the whole response (log the failure).
   - Add `GlobalSearchControllerTest.java` under `tt-data-league-api-rest/src/test/java/.../search/`, mirroring `PlayerControllerTest`/`ClubControllerTest` conventions: happy path with mixed results, short-query rejection, and one group failing without breaking the others.

5. **Frontend: API client** — Add `searchGlobal(query)` to a new `tt-data-league-frontend/src/api/search.js` (or alongside existing `players.js`/`clubs.js`/`matches.js` if a shared `api/` convention fits better), calling `GET /api/v1/search?q=...`, returning `{ players, clubs, matches }`.

6. **Frontend: hook** — Add `useGlobalSearch(query)` in `src/hooks/useSearch.js` (new file, mirroring `usePlayers.js`/`useClubs.js`), debounced 300ms with the same 2-char minimum used by `usePlayerSearch`/`useClubSearch`.

# Implementation Guidelines

- The global search entry point stays the existing Landing page `GlobalSearch.jsx` component (per the Goal); this feature does not add a second search box to `TopBar.jsx`/main navigation. Landing is reached via the app's default/home route, satisfying the "accessible from the main app navigation" acceptance criterion.
- Cap each result group to a small fixed number (proposed: 5) — the dropdown is a typeahead aid, not a full results browser. Full browsing stays on the existing dedicated Players/Clubs/Matches search pages; `/cerca` (`SearchResultsPage.jsx`) remains the Enter-key fallback and is out of scope for rewiring in this feature.
- Do not add new permission scopes: the aggregating endpoint must respect the same `players:read`/`matches:read` checks (and club's current no-extra-permission behavior) as the existing individual endpoints, per-group — a user without `matches:read` should get an empty Matches group rather than a 403 for the whole search.
- New match free-text search is intentionally unpaginated and capped — it is not a replacement for `MatchSearchCriteria`/`SearchMatchesQuery`, which keeps its mandatory `source`/`season` for the dedicated Matches search page.

- **Bug found via the user's own live Postgres run and fixed (2026-09-12)**: `MatchRepositoryHelper.searchByFragmentsInName` used `select distinct m from MatchJPA m ... order by case when m.matchDate is null then 1 else 0 end, ...`. Postgres rejects `ORDER BY` on an expression not in the `SELECT DISTINCT` list (`ERROR: for SELECT DISTINCT, ORDER BY expressions must appear in select list`). The `distinct` was copied from an unrelated query pattern that needs it because of a `join fetch` fan-out; this query has no such join (it filters via an `exists` subquery, matching the existing `search`/`countSearch` queries, which are not `distinct` either), so `distinct` was unnecessary. Removed it — no test caught this because the JPA-level test suite in this environment cannot run against a real Postgres instance (see the pre-existing `ApplicationContext`/`ImportRunRegistry` failure noted above); the mocked `FindMatchesByStringInNameQueryHandlerTest` never exercises the actual SQL.
